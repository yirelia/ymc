匹配 与 排序（Matching + BLT Sorting）

后端第一篇 · NBackEnd/Modules/1_Main/NBMatching.mo · NBSorting.mo

前两篇把模型压成了一张扁平方程表，本篇是后端拿到它之后做的第一件事： 给每个变量指派一条「负责求解它」的方程（匹配）， 再把方程排成一个能依次求解的顺序（BLT 排序）。 这两步合起来叫因果化（causalization）——把一堆无序的 = 关系， 变成一段有先后、可执行的计算流程。

1. 为什么需要这一步：= 不是赋值

扁平模型里的方程是数学等式，没有方向。resistor1.v = resistor1.R * resistor1.i 既可以「已知 R、i 求 v」，也可以「已知 v、R 求 i」。一个含 n 个未知量的模型，就是 n 个这样的无向等式。

但计算机要的是顺序执行的赋值：先算谁、后算谁。所以后端必须回答两个问题：

问题解决它的步骤输出
每个未知量由哪条方程来解？Matching（匹配）变量 ↔ 方程 的一一对应
这些方程该按什么顺序解？Sorting（BLT 排序）拓扑有序的方程块序列
前提：结构平衡 匹配的存在前提是方程数 = 未知量数。这正是前端 NFCheckModel 反复强调「模型必须 balanced」的原因——不平衡的模型在这一步根本无法匹配。

2. 二部图与邻接矩阵

把「变量」和「方程」看成二部图的两侧节点：若变量 v 出现在方程 e 里，就在 e 和 v 之间连一条边。 代码里这张图就是邻接矩阵 m——m[e] 是方程 e 里出现的所有变量下标列表（由 NBAdjacency 构造）。

模型: 二部图 (m[eqn] = 该方程含的变量): eq1: a = 2 eq1 ──── a eq2: b = a + 1 eq2 ──┬─ a eq3: c = b + a └─ b eq3 ──┬─ a ├─ b └─ c

匹配问题 = 在这张二部图里找一个完美匹配：给每条方程挑一个变量、每个变量恰好被一条方程挑中， 互不冲突。图论上这是经典的二部图最大匹配。

Part A — 匹配

3. Matching — 增广路径匹配 NBMatching.mo:340

入口 scalarMatching 的骨架非常直白：对每条方程，尝试找一条「增广路径」把它匹配到某个变量。 

var_to_eqn := arrayCreate(nVars, -1);       // -1 = 尚未匹配
for eqn in 1:nEqns loop                     // :359
  var_marks := arrayCreate(nVars, false);   // 本轮 DFS 的访问标记
  eqn_marks := arrayCreate(nEqns, false);
  (var_to_eqn, ..., pathFound) := augmentPath(eqn, m, mT, var_to_eqn, ...);   // :362
  if not pathFound then
    // 找不到 → 结构奇异，需要指标约简（见下一节）
    marked_eqns := ... :: marked_eqns;      // :369/371
  end if;
end for;

核心递归 augmentPath（:394）就是匈牙利算法的那一步，分两轮：

// 第一轮：有没有边直接连到一个「还没被占用」的变量？有就占它。
for var in m[eqn] loop                    // :405
  if var_to_eqn[var] <= 0 then            // 该变量空闲
    var_to_eqn[var] := eqn; pathFound := true; return;   // :406-409
  end if;
end for;

// 第二轮：都被占了 → 试着「请占用者让位」。递归地帮那条方程另找变量。
for var in m[eqn] loop                    // :415
  if not var_marks[var] then
    var_marks[var] := true;
    (...) := augmentPath(var_to_eqn[var], ...);   // :419 让现占用者去别处
    if pathFound then
      var_to_eqn[var] := eqn; return;         // :421 让位成功，我占下
    end if;
  end if;
end for;

一句话理解增广路径：「我想要的变量都被别人占了？那就问占用者能不能换一个。 只要顺着这条链最终腾出一个空变量，整条链集体挪一格，就多匹配上一对。」 对 n 条方程各跑一次，就得到完整的变量↔方程双射 var_to_eqn / eqn_to_var（:377-382）。

性能旁路 除了这份纯 MetaModelica 实现，还有 PFPlusExternal（:428）， 调用 C 外部库 BackendDAEEXT 里的 push-relabel 匹配，用于大模型。算法思想一致，只是换了更快的实现。

4. 匹配失败 = 结构奇异 → 指标约简 :364

如果某条方程怎么都找不到增广路径，说明这张二部图没有完美匹配——模型结构奇异。 这几乎总是因为模型是高指标 DAE：约束之间存在隐藏的微分关系，导致方程「数量够但结构上不够独立」。 

if not pathFound then
  if not partially then
    Error.addMessage(..., "structurally singular ... Index Reduction");   // :366
  else
    marked_eqns := BackendUtil.findTrueIndices(eqn_marks) :: marked_eqns;   // :371
  end if;
end if;

这里 marked_eqns 收集的正是「DFS 走过却匹配不上的那组方程」——它们就是需要被微分的约束。 下游的 NBResolveSingularities 用 Pantelides 算法对这组方程求导、引入 dummy derivative， 把指标降到 1，再回来重新匹配。经典例子是理想约束的摆锤 / 无质量刚性连接。

学习提示 指标约简（Pantelides + dummy derivative）是后端数学上最难的一块， 自成一篇。本篇只需记住：匹配失败不是 bug，是信号——它精确地指出「哪几条方程需要微分」， 这是 matching 除了排序之外的第二大价值。

Part B — 排序

5. Sorting — Tarjan 强连通分量 → BLT NBSorting.mo:307

匹配给了「谁解谁」，但没给顺序。eq2: b = a + 1 必须在 eq1: a = 2 之后算。 这种「依赖」把二部图变成了有向图： 

// predecessors: 方程 eqn 用到的变量，各自由哪条方程求解 → eqn 依赖那些方程
function predecessors(idx, m, mapping):        // :695
  pre_lst := list(mapping[cand] for cand guard(...) in m[idx]);

在这张有向图上跑 Tarjan 算法 求强连通分量（SCC），并且天然得到拓扑序。 tarjanScalar（:307）遍历每个已匹配变量对应的方程，未访问就进 strongConnect： 

for var in 1:N loop                          // :327
  eqn := matching.var_to_eqn[var];
  if eqn > 0 and number[eqn] == -1 then       // 尚未访问
    (stack, index, comps) := strongConnect(m, matching.var_to_eqn, eqn, ...);   // :330
  end if;
end loop;

strongConnect（:647）是教科书式的 Tarjan——number 是访问序号、lowlink 是能回溯到的最小序号、栈记录当前分量：

arrayUpdate(number, eqn, index);
arrayUpdate(lowlink, eqn, index);            // :663-664
stack := eqn::stack;

for eqn2 in predecessors(eqn, m, var_to_eqn) loop   // :670
  if number[eqn2] == -1 then
    strongConnect(... eqn2 ...);                        // 递归到未访问的后继
    lowlink[eqn] := intMin(lowlink[eqn], lowlink[eqn2]);   // :674
  elseif onStack[eqn2] then
    lowlink[eqn] := intMin(lowlink[eqn], number[eqn2]);    // :677 回边，同属一个 SCC
  end if;
end loop;

if lowlink[eqn] == number[eqn] then          // :682 eqn 是分量的根 → 弹栈成一个 SCC
  ... SCC := 弹出直到 eqn ...
  comps := SCC :: comps;
end if;

输出 comps 就是 BLT（Block Lower Triangular，块下三角）： 一个按依赖顺序排好的方程分组列表。每个分组（SCC）是一个「必须一起解」的块， 分组之间已经拓扑有序——照着从前往后算，每一块要用的输入都在前面算好了。

6. 代数环：多元素分块从哪来

SCC 的大小揭示了模型的结构。看两个对照例子：

A. 可依次求解（每块 1 个方程 = 下三角） eq1: a = 2 SCC1 = {eq1} → a := 2 eq2: b = a + 1 SCC2 = {eq2} → b := a + 1 eq3: c = b + a SCC3 = {eq3} → c := b + a 三个单元素块，直接顺序赋值，无需迭代。 B. 代数环（一块含多个方程 = 需联立） eq1: x + y = 3 SCC1 = {eq1, eq2} → 2×2 线性系统，一起解 eq2: x - y = 1 x 依赖 eq2、y 依赖 eq1，互相引用 → 强连通 → 同一个块。
SCC 大小含义后端怎么处理
1 个方程可直接解出一个变量生成一句赋值（必要时符号求解 NBSolve）
多个方程代数环：一组变量互相耦合线性 → 生成矩阵求解；非线性 → 交给 Tearing 撕裂后用 Newton 迭代

这就接上了下一步：Tearing（NBTearing.mo）的存在意义，正是为了把这些多元素 SCC 尽量缩小—— 选出少量「撕裂变量」当迭代未知量，其余变量用它们显式表达，把一个大的非线性块变成一个小得多的迭代问题。

7. 全景图与下一步

扁平方程表 (前两篇的产物: 纯变量 + 纯方程, #eqn = #var) │ ▼ NBAdjacency 构造邻接矩阵 m[eqn] = 该方程含的变量 二部图 │ ▼ NBMatching augmentPath 增广路径 → 变量↔方程 双射 │ 匹配失败? → marked_eqns → 指标约简(Pantelides) 匹配 (谁解谁) │ ▼ NBSorting predecessors 定向 → Tarjan SCC → 拓扑序 BLT 分块 (谁先算 + 哪些要联立) │ ├─ 单元素块 ─────────► NBSolve 符号求解成一句赋值 └─ 多元素块(代数环) ──► NBTearing 撕裂 + Newton 迭代 │ ▼ 可执行的计算序列 → SimCode → C 代码 → SUNDIALS 积分

到这里，「无序的等式集合」已经变成「有先后、可执行的计算流程」。 匹配 + 排序 = 因果化，是符号求解型仿真编译器的心脏。剩下的 Tearing、指标约简、符号雅可比， 都是围绕这张 BLT 图做的进一步优化与特例处理。
