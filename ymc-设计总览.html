ymc 编译器设计总览

整合篇 · 设计思路 · 难点账本 · 分阶段路线 · 基线 OMC 3ceb0c9d06（新前端 NFFrontEnd/ + 新后端 NBackEnd/）· 规范 MLS 3.6 · 2026-09-14

一句话：Modelica 编译器不是在翻译语句，而是在把一组面向对象的方程压平成方程组，再把方程组因果化成一个能按时间步进求值的程序。 ymc 的设计思路只有一条主线：拿 OMC 当标准答案，把这条流水线切成可以单独验证的段，每段用 C++ 重写、用 OMC 的输出差分验收。

本文与其他文档的关系。 《自研编译器技术方案-C++.md》是规范（编码规则、可调试规则、验收命令、任务卡模板），本文是地图：先看全局，再看每个难点难在哪、OMC 怎么做、ymc 打算怎么做、怎么验证。 八篇 OMC 导读是每个难点的细读。三者的分工见 §7 文档地图。文中所有 OMC 行号都已在基线提交上 grep 核对；所有"OMC 现状"都来自实跑。

两条接缝为什么重要

接缝 ①：Base Modelica / FlatModel 文本

OMC --baseModelicaOptions 把新前端的 FlatModel 打成标准文本（NFInst.mo:227-229 / :247-249 → InstUtil.dumpFlatModel）

它同时是前端的验收 oracle和后端的输入格式。后果：后端（S5）可以拿 OMC 产出的 Base Modelica 文件启动，不必等前端（S3，最重的阶段）写完；调试时可以把出错阶段的输入存成文件反复重放。

接缝 ②：运行时回调表 ABI

include/omc/c/openmodelica_func.h:56 struct OpenModelicaGeneratedFunctionCallbacks（functionODE :109、functionAlgebraics :113、functionDAE :117、functionInitialEquations :163 …）

S6 生成的 C 只要填满这张表、链接 OMC 1.25.0 的 libSimulationRuntimeC，就能白嫖 OMC 全部求解器、事件处理、初始化、结果文件来做数值验收。S7 再一块一块换成自研运行时，每换一块都有"正确答案"可比。这条接缝把"运行时数值鲁棒性"这个最难磨的问题推迟到了后端已经正确之后。

2. 六个核心设计决定

这六条是"第一天定下、之后改不动"的决定。每条写清楚为什么，因为你以后会在某个深夜想推翻它们。

D1 IR 用 struct + enum class Kind + switch，不用继承、不用 std::variant

OMC 的 MetaModelica 代码 90% 是 match + 不可变 uniontype，翻成 C++ 有三条路：class 继承 + visitor（啰嗦，调试器里看到的是基类指针）、std::variant + std::visit（编译慢、模板报错读不懂、调试器里看不清）、tagged struct + switch。选第三条，原因只有一个：它最接近 match 的原味，且配 -Werror=switch / /we4062 能得到编译期穷尽检查：新增一种 ExprKind，所有漏处理的 switch 一起报错。这是保证"改一处、全链路一致"的唯一廉价手段。

D2 内存：Arena + 强类型 Id<T> + Symbol 驻留，IR 里禁止 shared_ptr 和裸指针

OMC 的实例树（InstNode）是可变、大量共享的：一个类节点被几百个组件引用，修饰沿树往下推时原地改。C++ 里要么 shared_ptr 到处飞（循环引用、调试器里全是引用计数），要么 arena 拥有一切、节点之间用 32 位整数 Id 互指。选后者，附带三个好处：Id 稳定且可打印（两次运行同 Id，dump 能对比）；Id<Expr> 和 Id<Var> 是不同类型，传错直接编译错；序列化天然简单。代价是一条必须刻进肌肉的规则：持有 Id，不持有引用跨越 add()——vector 扩容会让引用悬垂，这是你在 T-S0-02 里要亲手做的实验。

D3 每个 pass 有文本 IR，至少 Base Modelica 与 .bdae 可回读

这是"全部可调试"的核心机制：--dump-after=<pass> 看任意一层，--from=<file> --run=<pass> 单独重放一层。它同时决定了工程顺序：后端可以在前端完成前用 OMC 的输出开工。格式对齐 OMC 的 dump（-d=bltdump、-d=dumpSimCode），并排 diff 才有意义。

D4 先标量化，数组保持留作研究题

OMC 新后端最大的特色是不标量化（for 方程整段保留，causalizePseudoArray NBCausalize.mo:247），这是团队做了多年还在做的事。ymc 第一版走 NFScalarize（NFInst.mo:236）那条路：全部展开成标量。代价是 MSL 大模型编译慢、生成的 C 大；收益是后端所有算法回到教科书形态（邻接矩阵是 0/1、匹配是标准二分图匹配），验收也简单。数组保持排 S8 之后，作为独立研究题。

D5 运行时先借后换

见接缝 ②。数值鲁棒性（事件定位、步长控制、同伦初始化、非线性求解器的阻尼）是"只能靠海量模型磨"的东西，没有正确答案就自己写，等于在没有测试的情况下调数值代码。先借 OMC 运行时把后端验证到 L2，再逐块替换，每块替换都是差分回归。

D6 确定性：影响输出顺序的遍历禁止走 unordered_*

L1 验收是文本 diff，OMC 的变量/方程顺序是确定的，ymc 必须复现同一顺序。这条规则逼你把遍历顺序做对，也让"同一输入两次运行 byte-identical"成为一条随时可查的不变量。

3. 难点账本

每条难点固定四栏：难在哪 / OMC 现状（实证）/ ymc 策略 / 怎么验证。难度标签：硬 研究级或规范空白多；中 算法清楚但细节多；体力 量大但路清楚。

3.1 前端：真正的硬骨头（占总工作量 60% 以上）

难点不在解析，在实例化。解析器手写递归下降一两周就能过 MSL；难的是把面向对象的模型变成 FlatModel 那一步。OMC 新前端 NFFrontEnd/ 是 81,913 行 MetaModelica（今日统计），而且已经是重写过一次的干净版。

F1 名字查找与作用域 中

MLS 3.6 §5 · OMC NFLookup.mo、NFInst.mo:185 instantiateRootClass

难在哪
嵌套类、import 四种形式、encapsulated 截断、inner/outer 跨层配对、enclosing scope 逐层回溯、extends 引入的名字与本地名字的优先级、条件组件。规则本身能背下来，组合起来的边角非常多。
ymc 策略
S3a：先做无数组、无修饰的骨架，实例树 = arena + Id；每条查找规则的函数头注释引用 MLS 小节。
验证
flattening/modelica/scoping、packages、declarations L1 全 PASS。

F2 修饰合并 + 继承 + redeclare 硬

MLS §7（继承、修饰、重声明）· OMC NFInst.mo:194 instExpressions、NFModifier.mo、NFInst 的 expand

难在哪
extends A(x=1, redeclare B b) 的修饰要沿继承链和组件树往下推、合并、覆盖；each、final、replaceable/constrainedby 的类型约束检查；redeclare class 与 redeclare component 语义不同。这是 Modelica 里出名最绕的一块，MSL 的每个 Interfaces.Partial* 都在用它。
ymc 策略
S3b。修饰合并单独 dump（对齐 OMC 的 modifier 打印），每个规范角落一个探针模型 + OMC 输出存档。
验证
extends、modification、redeclare、scodeinst 子集 L1。

F3 类型系统与数组维度 中

MLS §6（类型关系）、§10（数组）· OMC NFTyping.mo:124 typeClass（typeComponents :140 → typeBindings :950 → typeClassSections :2727）、NFType.mo、NFDimension.mo

难在哪
结构化子类型（插头兼容）；数组维度可能来自绑定值或 :（未知，要从绑定反推）；Real 的属性（unit/min/max/start/nominal）是类型的一部分；切片、for 表达式、归约；函数重载靠 operator record。

验证

F4 编译期求值 = 编译器里内置一个 Modelica 函数解释器 硬

MLS §12（函数）、§3（表达式）· OMC NFCeval.mo、NFEvalFunction.mo、NFEvalConstants.mo、NFInst.mo:198 updateImplicitVariability

难在哪
数组维度、结构参数、if 方程的参数条件都要在编译期算出来，所以编译器必须能执行 Modelica 函数：record、数组、循环、递归、以及白名单内的 external "C"（MSL 的表格与字符串函数）。变量性推断（哪个 parameter 其实是 structural）决定了什么必须求值。
ymc 策略
S3e。解释器的值系统与 S4 脚本层的 Values 共用；外部 C 函数白名单从 MSL 实际用到的列表倒推。
验证
algorithms-functions、records、external-functions、external-objects（L1）；functions_eval（L2）。

F5 connect 语义：flow / stream / expandable / 过约束图 硬

MLS §9（连接）、§15（流连接器）· OMC NFFlatten.mo:2433 resolveConnections、NFOCConnectionGraph.mo、NFArrayConnections.mo · 细读：《NFFlatten-方程与连接导读》

S3d。连接集用并查集；过约束图单独一个 pass、单独 dump。

F6 平衡检查与诊断质量 中

MLS §4.7（平衡模型）· OMC NFVerifyModel.mo（NFInst.mo:262）

难在哪
"连接器的势变量数 = 流变量数"、partial 类的计数规则、模型是否平衡——规则本身一页纸，但用户对工具的第一印象就是报错说了什么。而且 L3 验收要求 getErrorString 的文本和 OMC 一致（3269 个文件用它）。

F7 语法本身 体力

MLS 3.6 文法附录 · OMC Parser/Modelica.g（stored_definition :225、表达式 :1554、脚本语句 :2246）、Dump.mo（反解析）

难在哪
不难，但宽：注解（annotation）是完整的修饰语法；. 与数字、Q-IDENT、字符串转义的词法边角；表达式优先级；.mos 脚本语句和表达式共用文法。手写递归下降 + Pratt 表达式解析足够，禁止解析器生成器是为了让你完全掌控错误恢复。
验证
round-trip：parse → unparse → parse → unparse 两次输出 byte-identical，对 2641 个 .mo + 整个 MSL。这是免费的大测试。

F8 MSL 4.0.0 全量压平 = 真正的前端验收 硬

MSL 位置 %APPDATA%\.openmodelica\libraries\Modelica 4.0.0+maint.om · 验收 oracle：OMC instantiateModel / Base Modelica 输出

难在哪
MSL 用到了 F1–F7 的每一条，而且是同时用。OMC 前端能到今天，靠的是上千个 testsuite 用例和十几年"Dymola 是怎么做的"的经验——规范有大量空白角落。另外是性能：大模型压平要快，cref 哈希、避免深拷贝、interning 缺一不可（OMC 新前端花了几年才快起来，基线耗时待测，方案 §8 #5）。
ymc 策略
S3g 用 MSL 全部 Examples 的 L1 diff 作为退出条件；通过率报告按包分类，逐包攻。

F9 同步时钟与状态机（第一版不做）硬

MLS §16、§17 · OMC NBPartitioning.mo:472（时钟分区）

单独两章规范，有自己的分区、求解和代码生成路径。testsuite 里 synchronous 22 + synchronous_c 18 + 状态机 14 个用例，标 skip 计数，S8 再做。

C++ 特有的痛。OMC 前端到处是"一个节点被很多地方共享并原地修改"，这正是 D1/D2 在第一天就要定死的原因。你会踩的第一个大坑不是算法，是arena 扩容后悬垂引用——T-S0-02 的强制实验就是为了让你在 100 行代码里先踩一次，而不是在 3 万行里。

3.2 后端：算法都有论文，难在"配合"

单个算法不难：匹配、Tarjan、Pantelides 各是几百行。难的是它们互相咬合的地方，也正是这几天在新后端里实证看到"留白"的地方。OMC 新后端 33,047 行、旧后端 125,409 行（今日统计）——后者的体量差就是"配合"的成本。

B1 别名消除 中

OMC 2_Pre/NBAlias.mo:118（1,363 行）；旧后端 RemoveSimpleEquations.mo 更大

难在哪
看着简单（a = b 合并），实际要处理符号与增益、start/nominal/min/max 属性冲突、留谁当状态（StateSelect、fixed）、替换要贯穿 when/initial 段。实证：Demo 模型里 Alias 模块把 y 选成了状态而不是 x，这类"哪个变量活下来"的决定直接影响后面每一层的 dump。
ymc 策略
S5a。别名集用并查集 + 代表元选择规则显式写成表（优先级：StateSelect > fixed start > 用户变量 > 生成变量）；代表元选择单独 dump 并与 OMC 对比。

B2 匹配 + 排序（因果化） 体力

OMC NBCausalize.mo:247；NBMatching.mo:394 augmentPath（增广路）、:428 PFPlusExternal（外部 C 实现的 PF+）；NBSorting.mo:233 tarjan；NBAdjacency.mo:81 strictness / :838 refine · 细读：《NFBackend-匹配与排序导读》

难在哪
算法是教科书的（增广路二分匹配 + Tarjan 强连通分量）。难点在邻接矩阵怎么建：一个变量出现在方程里不等于能从这条方程解出它（可解性靠偏导判断，OMC 用 strictness 分级），以及 NB 的伪数组邻接。ymc 走标量化，邻接就是 0/1 矩阵，这一条被 D4 简化掉了。
验证
backenddaeinfo 的强连通分量按类型计数、bltdump 块大小序列与 OMC 一致。

B3 指标约简 + 状态选择 硬（对标 Dymola 的第一道分水岭）

Pantelides 1988；Mattsson–Söderlind 1993（哑导数）· OMC NBResolveSingularities.mo:67 indexReduction、:450 getMSSS、静态/动态分支 :292-308；NBMatching.mo:119 singular · 细读：《NB-指标约简导读》

OMC 现状（实证）
1.25.0 发行版的新后端没有指标约简；工作区 dev 版有 Pantelides + 静态哑导数，动态状态选择分支直接 fail；带 StateSelect 的单摆（PendulumSS）让 dev omc 陷入无限循环并写出 1.5 GB 输出。动态选择只在旧后端 BackEnd/IndexReduction.mo（StateSet）+ 运行时 stateset.c。
难在哪
Pantelides 只是前半段。单摆这类模型要在运行时按雅可比主元换状态，编译器（StateSet 生成、每个候选集的方程）和求解器（stateset.c）要配合。这是 Dymola 稳定支持而 OMC 新后端还没做到的能力。
ymc 策略
S5c 做 Pantelides + 静态哑导数（与 dev NB 对齐，可差分）；动态状态选择放 S8，参照旧后端 + 运行时接口（方案 §8 #9 待读）。
验证
indexreduction（8）、start_value_selection（8）；动态选择用例在 S8 前标 skip。

B4 符号微分 中

OMC Util/NBDifferentiate.mo

难在哪
四个客户共用它：指标约简（方程求导）、雅可比、线性判定、方程求解。要支持 annotation(derivative=…) 的函数、record、数组、smooth/noEvent、der 的嵌套。任何一处微分规则错，四个客户一起错。
ymc 策略
S5c 先做指标约简够用的子集，S5e 扩到函数与雅可比；每条微分规则一个单测快照。

B5 方程符号求解 中

OMC NBSolve.mo:92 main / :637 solveBody（solveSimple / solveLinear / solveUnique）

难在哪
f(x) = g(x) 解出 x：线性提取、逆函数、"唯一出现"判定、除零保护、if 表达式两支都要解。这类代码写起来全是特例，OMC 的规则集是多年积累的。
ymc 策略
S5e。规则表驱动 + 解不出就退化为非线性块（永远有正确但慢的兜底）。

B6 撕裂 + 线性/非线性判定 硬（对标 Dymola 的第二道分水岭）

Elmqvist–Otter 1994；Cellier–Kofman 2006 · OMC NBTearing.mo:138、getModule :243、minimal :403、checkLinearity :598；旧后端 BackEnd/Tearing.mo（cellier / omcTearing，方案 §8 #8）· 细读：《NB-撕裂导读》

OMC 现状（实证）
新后端 --tearingMethod=cellier 实际映射到 minimal，而 minimal 只处理离散子系统；checkLinearity 对连续环恒为真（空判定）；所有代数环都变成 SES_NONLINEAR（NSimStrongComponent.mo:640），_03lsy.c 为空；环的雅可比被 if false 丢弃（:756）。也就是说，新后端的撕裂与线性求解路径目前是占位。
难在哪
Cellier 启发式本身不难，难在和线性/非线性判定、初始化系统、混合系统三方配合，以及撕裂变量的选择对数值收敛的影响（这是 Dymola 的看家本领之一）。
ymc 策略
S5e：自己做线性判定（对撕裂后的残差方程求雅可比、检查是否与未知量无关）→ 线性块走 LAPACK/KLU；非线性块做 Cellier 撕裂，参照旧后端实现范围。
验证
tearing（108）、nonlinear_system（61）、linear_system（16）、resolveLoops（13）。

B7 初始化系统 中

MLS §8.6 · OMC NBInitialization.mo:82（createStartEquation :206、createParameterEquation :413）、NBResolveSingularities.mo:344 balanceInitialization、NBCausalize.mo:262（三阶段匹配）· 细读：《NB-初始化系统导读》

OMC 现状（实证）

难在哪

ymc 策略
S5d 完整复刻 NB 的流程（可差分）；诊断消息对齐 OMC。
验证
initialization（91）。

B8 事件与混合系统 硬（最想警告你的一条）

MLS §8.5（事件）、§3.7（事件相关算子）· OMC 2_Pre/NBEvents.mo:88（关系式 → $SEV/$TEV）；运行时 solver/events.c、perform_simulation.c.inc:383

难在哪
过零函数提取、关系式滞回、sample 时间事件、when 的优先级与嵌套、pre/edge/change、reinit、事件迭代（同步数据流原则：事件后迭代到不动点）、连续/离散混合环。自己写的仿真器 90% 在这里"差一点"：抖振、漏事件、when 触发顺序错。

验证

B9 数组保持（不标量化）硬（研究题）

OMC 新后端的核心卖点，团队做了多年还在做。ymc 第一版按 D4 全标量化；等 MSL 大模型的编译时间成为实际瓶颈时再作为独立研究题立项。

3.3 代码生成与运行时：不难但很宽

C1 与 OMC 运行时 ABI 对齐 体力

openmodelica_func.h:56；数据布局 simulation_data.h；变量下标顺序 NSimVar.mo:213 traverseCreate（状态 → 导数 → 代数 → 离散 …）；文件切分 SimCodeMain.mo:589-611；_init.xml / _info.json 序列化 · 细读：《NB-Susan模板与代码生成导读》

回调表几十个字段，哪些可为 NULL、变量数组的下标约定、equationIndexes 与 #line 的对应，都要逐字段对齐。方案 §8 #7 待验证：1.25.0 的公开头文件是否够用（不需要 OMC 私有头）。ymc 不用 Susan 模板，用手写的 C 打印器（AST → C），因为模板语言本身是另一门要学的东西，而且不可调试。

C2 生成代码的体量与编译时间 中

全标量化后 MSL 大模型会生成几 MB 的 C，优化编译要几分钟。第一版接受；长期的两条出路是 for 循环保持（NB 的 genericCall 思路）或 JIT。生成阶段本身要注意 std::string += 的二次方陷阱（用 fmt::memory_buffer）。

C3 自研运行时的数值鲁棒性 硬

OMC solver_main.c:599、initialization.c:753、nonlinearSolverNewton/Homotopy.c；MAT v4 写出 simulation_result_mat4.cpp

积分器可以链 SUNDIALS（CVODE/IDA）和 LAPACK/KLU，但事件定位（root function + 二分）、事件后重启求解器、步长控制与不连续点、同伦初始化、MAT v4 结果文件、参数覆盖、日志——这些胶水加起来体量和后端同级（OMC SimulationRuntime/c 83,584 行 C），而且数值鲁棒性只能靠海量模型磨。这就是 D5 的全部理由。ModelicaExternalC（MSL 的表格/文件/字符串函数）BSD 许可，直接链。

3.4 贯穿始终的工程难点

E1 没有测试就是盲飞 硬

全部重写最大的风险。解法就是本文的主线：OMC 当 oracle，每层差分——前端比 Base Modelica 文本（L1），后端比 bltdump / backenddaeinfo 的结构，仿真比 _res.mat（L2），脚本比逐语句输出（L3）。日常主工具是 tools/diff_omc.py M.mo：同一模型分别过 OMC 与 ymc，逐阶段并排 dump，第一处不同即停。前提是 S0 把运行器做对：运行器对 OMC 自身跑 scoping 目录必须全 PASS，否则它报的 FAIL 没有意义。

E2 旧前端用例的文本不可比 中

2030 个 -d=-newInst 用例只做数值级；有多少在数值级仍与新前端一致，是方案 §8 #2 待测的数字。它决定了 L2 验收的真实上限。

E3 输出格式与错误消息逐字对齐 体力

L3 要求 true、""、record 打印、getErrorString 文本与 OMC 一致。omc-diff 的模糊比对规则（浮点容差、空白）尚未复刻（§8 #1），这是 S0 剩余的基建之一。

E4 编译器自身性能 中

MSL 压平的耗时基线待测（§8 #5）。设计上已经预留：Symbol/cref 驻留、arena、hash-consing、无深拷贝的 Id 引用。规则是先正确再快，但数据结构要从第一天就不给"慢"留后门。

E5 C++ 本身，对一个基础弱的人 硬

未定义行为不会报错、迭代器失效、所有权、模板报错读不懂。应对全在方案 §3.4/§3.5：IR 不用指针、不用 shared_ptr、不用 variant、核心算法不写模板、ASan 每周全量、每个 pass 先写 dump 快照再写代码、VS 图形调试器为主。每张任务卡把该任务会踩的坑提前标出来，你踩一次记一条 lessons。

E6 规范空白 中

很多角落是"Dymola 怎么做就怎么做"。ymc 的规则：写不出 MLS 章节 / OMC 函数 / 探针模型三者之一的来源，就不写代码，进 open-questions.md。探针模型库（每个规范角落一个最小模型 + OMC 输出）是 S3 的固定配套。

5. 验证体系：为什么这条路线能走稳

级别比什么oracle 命令（OMC 侧）适用
L1 文本压平输出经归一化后与 // Result: 块一致；变量/方程顺序不排序（必须复现 OMC 顺序）omc -d=newInst M.mo；--baseModelicaOptionsflattening/**/*.mo（2641）、instantiateModel（179 个文件）
L2 数值.mat 逐变量插值比对，容差对齐 diffSimulationResults(reltol, reltolDiffMinMax, rangeDelta)（CevalScriptBackend.mo:2373）simulate + compareSimulationResults / diffSimulationResults / valsimulation/**/*.mos（2626）
L3 脚本.mos 逐语句输出与 // Result: 一致omc script.mos所有 .mos
结构级（S5 专用）backenddaeinfo 统计、bltdump 块大小序列、邻接矩阵 dumpomc --newBackend -d=bltdump,backenddaeinfo --simCodeTarget=None -s M.mo后端每个 pass

三个"证明测试本身正确"的动作，缺一个整套验收就是自欺：

  1. 运行器先对 OMC 自身跑，全 PASS 后才用于 ymc（S0）。
  2. 每个 pass 先写期望 dump 快照，再写代码（方案 §3.5 第 11 条）。
  3. skip 清单有文件、有原因、有计数；通过率报告永远显示"PASS / FAIL / SKIP"三个数，不只显示 PASS。
跑 OMC 做 oracle 的两个坑。① 工作区 dev omc 对 index-3 + StateSelect 模型会无限循环并写出 GB 级输出，务必带超时；② 安装版 1.25.0 与工作区 dev 版的新后端行为不同（前者无指标约简），差分时写清楚用的是哪一个。
